## 剩余问题

### S01 [P1] 预算检查、预留和结算不是一个事务（R01）

位置：`app/knowledge/budget.py:80-162`。

`reserve()` 在事务外取 totals 和判断，随后另开事务插入。同一 ledger 两个并发请求、总上限 10、各预留 6，**两次都成功，总预留 12**。进程内锁也没有覆盖整个判断和写入，多个 worker 更不能靠该锁防止超限。

页数只统计 `usage_events.kind='vision'`，不计未决预留；unknown 用 `vision-page` 记账也不计页。上限 1 的探针连续接受 3 个页请求，pages 仍为 0。`settle()` 先提交 settled 再写 usage，中间中断后 8 token 消费消失，剩余额度重新变为 10；`fail_unknown()` 有同类窗口。

应把检查+预留、状态转换+usage 分别做原子事务，结算用唯一关联键保证重放幂等，页预留持久化。还须覆盖实际 HTTP 重试、usage 缺失、响应已返回但向量格式错误等调用后状态：缺 usage 不能当真实零消费，已发出的请求不能简单 release。后几项为静态审查范围，独立探针已直接复现前三类。

### S02 [P1] 最后一次哈希检查后仍会覆盖人工编辑（R10）

位置：`app/knowledge/writeback.py:139-150`。

加锁和二次读取只约束本服务写者；编辑器/Syncthing 不遵守该锁。在最后一次检查后、`os.replace` 前写入人工文本，探针返回 `written`，最终文件是 `machine-v2`，人工文本丢失。不存在通用的“读取哈希后条件式 replace”保证。

将可人工编辑的成果改为不可变、唯一命名的追加输出；若需要 latest 指针，限定为独立的机器元数据。保留既有笔记和候选，不能以“缩小竞态窗口”关闭“不覆盖人工编辑”的要求。

### S03 [P1] public as_of 把报告日期当公开时间，存在未来信息泄漏（R08）

位置：`app/knowledge/indexing.py:226-228`；`docs/adr/0007-index-selection-and-asof.md`。

公开时间优先取 `report_date`。合成文档报告日期 6 月 30 日、明确 published_at/filing_date 为 8 月 20 日，查询截至 7 月 1 日仍命中。报告期末或落款不能无条件代表可公开获得的时间；文档级时间也不能证明修订版本当时已公开。

须保存版本级公开时间依据、来源及 unknown 状态，并明确日期精度、时区及边界。ADR0007 另将历史查询收窄为“当前内容按时间过滤”，旧版证据 URL 不能代替当时语料的历史全文搜索。应明确 API 能力，不能把该收窄直接记作原历史研究需求验收通过。历史模式需按截止时间选当时可知版本；不能可靠重建时显式拒绝/标记不支持。

### S04 [P1] 快照 API 验证的字节和返回的字节可能不同（R04/R11）

位置：`app/knowledge/kbapi.py:298-308`。

`verify_blob()` 完成后重新打开路径读文件。探针在校验结束后改写合成 blob，接口返回新内容，却仍携带旧 SHA 的 ETag。提取路径已修复的原则没有覆盖服务路径。

必须校验实际将返回的同一份字节；大文件如流式处理，设计先验证后发布且不可变的读取来源，不能在发出正文后才发现失败。并发改写时返回原正确字节或明确失败，禁止错误证据搭配原身份。

### S05 [P1] 低置信度 PDF OCR 仍可标为 ready（R05）

位置：`app/knowledge/extract.py:713-766`。

OCR 置信度只记录在 issues 字符串，没有进入块质量或文档门禁。合成单页 PDF 的 OCR confidence=0.1、配置 min_confidence=0.6，只要文字够长，文档和块均为 ready。正文长度不能证明数字/金额可靠。

须逐页传播置信度和失败原因；低置信度、空结果、回退失败/预算拒绝且原结果不达标，均不得因其他页文字足够而 ready。金融数值门禁继续独立验收，不以该 mock 代替真实盲测。

### S06 [P2] 图片重试仍重复运行 OCR（R02）

位置：`app/knowledge/jobs.py:202-213`；`app/knowledge/extract.py:104,813`。

预查身份使用 `stdlib-image`，实际保存使用 `stdlib-image+<engine>`，因而命中检查发生在 OCR 之后。相同图片、快照和配置连续执行两次，返回同一 extraction，但 OCR 被调用两次。付费图片 OCR 会产生重复消费。

统一预查和最终产物身份，并覆盖并发领取、失败后恢复、主/回退引擎变更；“数据库无重复行”不是“零重复昂贵处理”。

### S07 [P2] 新版本提交与影响 outbox 入队之间仍可丢任务（R15）

位置：`app/knowledge/sync.py:130-139`。

`upsert_versions` 已提交，才调用 `enqueue_impact`。在入队处中断并重跑同步，版本存在、new_versions=0、pending impacts=0，之后无变更的周期也不会补回。现有测试在完整 sync 之后模拟崩溃，没有覆盖此窗口。

版本插入与 outbox 必须同事务，或用可证明完整的持久对账修复机制；已有缺失行须可非破坏性补齐。消费重试、ack 之前中断也要保持候选幂等。

### S08 [P2] 文档元数据变化不使搜索游标失效，后续页漏结果（R12）

位置：`app/knowledge/indexing.py:134-137`；`app/knowledge/kbapi.py:153-195`。

generation manifest 没有纳入过滤用元数据，但每页查询读取实时元数据。A/B 文档各两块，先读两条，再把第一页文档 available 改 false；同一游标第二页为空、next_cursor=null，而仍有 2 条可见结果，B 被跳过。

将影响筛选/排序的修订纳入游标身份，变更返回明确 409；或提供固定搜索快照。冻结分页也不能绕过实时撤权检查。测试除 available 外还应覆盖 symbol/date/collection 等。

### S09 [P1] 全栈 library 启动错程序；构建失败被吞；切换命令目录错误（R13）

位置：`deploy/docker-compose.full.yml:27-36`；`Dockerfile.knowledge:16-17` 及末行 CMD；`deploy/CUTOVER.md` 步骤 1、4、5。

1. library 共用知识层镜像，但没有覆盖 command；镜像 CMD 是 `python -m knowledge worker --config /app-config/knowledge.json`。library 仅挂 `/app/config/config.json`，不会启动旧第一层 `library serve`，默认配置路径也未挂入该服务。必须核对每个服务的最终进程、配置、端口。
2. `pip install ... && python ... || true` 会同时吞掉依赖安装失败和 OCR 预热失败，构建成功不再保证所需能力存在。
3. 步骤 1 `cd $OLD/repo` 后，步骤 5 用相对 compose 文件启动，未切回 `$NEW/repo/deploy`，在停旧栈后会找错文件。步骤 4 的 writeback 又使用宿主 `$NEW/vault`，worker 实际挂载路径为 `/vault`，配置需统一容器视角。

两份 YAML 的本地语法解析通过，但不能据此验收启动行为。修复后在隔离数据目录验证第一层、知识 API、worker 的实际进程与健康端点，再按切换手册从任意 cwd 演练；本轮不授权真实停服/切换。

### S10 [P2] 混合检索仍没有独立语义召回（R09 剩余范围）

位置：`app/knowledge/analysis.py:120-130`。

已修复先筛选的安全问题，但 `pool_ids = keyword_ids or allowed[:embed_top]` 意味着只要有一条词法命中，其他纯语义相关块就绝不进入向量召回；完全无词法命中时又只看固定前 200 块。原任务书要求的独立双路召回未实现。embedding 缓存仍仅以 model 与 block 取值，缺少 provider/维度等隔离。

独立探针用确定性向量验证：弱词法文档 K 返回，强语义文档 S 被遗漏；缓存隔离为静态代码结论。回归应保留“一个弱词法命中 + 一个强语义零词法命中”测试，要求后者仍进入融合候选；用同名模型不同 provider/维度验证缓存隔离。真实 embedding 仍关闭，不需付费验证。

## 对整合方案的建议

继续保留单仓库、一个权威 catalog、独立知识数据库的设计，无需再次搬迁或重做 M0。部署镜像可以共享，服务职责必须显式配置；现有旧服务和 OCR 回填是当前运行状态，不能靠 README 的过期“尚未回填”描述判断。

自动化长期运行的边界应落在数据库原子提交、版本时间证据、不可变成果与可恢复任务上。当前最主要问题是这些边界的失败情况覆盖不足。优先补交错执行/事务中断测试，再进行真实质量和持续运行验收；不要继续用增加 happy-path 测试数量替代门禁。
