## 剩余问题及证据

### T01 [P1] 旧数据库无法启动迁移（新升级回归）

位置：`app/knowledge/store.py:204,316-320`。

`__init__` 先执行完整 SCHEMA，其中新建索引引用 `usage_events.reservation_id`，随后才 `_migrate()` 添加该列。用 Git 基线 `0a473d9` 的完整 SCHEMA 创建数据库，再用当前 KnowledgeStore 打开，立即报 **`no such column: reservation_id`**。新建空库的 287 回归无法发现已有运行数据库的升级失败。

修复须区分建库与升级：依赖新列的索引在加列后创建，迁移版本与顺序明确。用至少上一部署 schema 的有数据副本验证，重复打开、失败重试、历史 usage/证据/任务保留均要断言。禁止删库重建绕过。

### T02 [P1] 未知结算、坏响应和 HTTP 重试仍破坏预算（S01 未闭环）

位置：`app/knowledge/budget.py:197-214`；`app/knowledge/analysis.py:53-58`；`app/knowledge/providers.py:97-123`。

- `fail_unknown()` 仍先提交 unknown 状态，再另写 usage。消费预留 8/上限 10，在写 usage 前中断，剩余回到 **10**、usage=0；unknown 输入 token 不在预留汇总中。
- 对同一 reservation 调用两次 `fail_unknown()`，记入 **16 token / 2 calls**，而不是一次 8；没有 reservation 唯一关联的异常账目不可幂等恢复。
- embedding 已返回结果和 usage，但向量形状错误会 `release()`。合成已消费 5 token 的坏响应变成 **usage=0、全部额度可用**。
- HTTP 层内部重试没有逐次请求预留。请求上限 1，mock 两次超时仍发生 **2 次 HTTP 尝试，账本只计 1**。

修复必须覆盖整个调用状态机，成功和异常共用唯一请求/尝试身份。未知消费保守占用，已发出后的错误不能退回零成本；每次物理请求都经过请求数门禁。真实账单、估算、unknown 分开记录，不能把估算标成供应商实测 usage。

测试证据限制：新增 `settle_crash_before_usage()` 只是直接 raise 的独立方法，现有测试调用它不能证明真实 `settle()` 中间写入的事务回滚。应在实际持久化路径注入故障，或用独立进程在明确检查点中断。

### T03 [P1] 版本级字段仍由文档旧公开日期填充（S03 未闭环）

位置：`app/knowledge/store.py:408-437`；`app/knowledge/indexing.py:316-327`。

新增 `public_available_at` 字段有用，但无版本证据时自动拷贝文档 `published_at/filing_date`。合成文档 v1 在 1 月公开，v2 在 8 月首次观察、没有 v2 的公开依据；v2 被填入 **1 月 1 日**，7 月 public 查询仍返回 v2 内容。把旧日期复制到新列不能证明新版本当时已公开；不能以首次接入时间替代公开时间修复。

明确来源适配器何时能把文档级发布日期可靠绑定到具体版本；不能证明则保留 unknown。时间修正应保留依据和历史，不把新值无审计覆盖到所有旧版本。补 v1/v2、unknown、发布时间更正和日期/时区边界用例。

能力差距：默认索引仍只有当前版本，ADR0007 的“证据重放”不等价于历史全文检索；其 report_date 公开依据描述也已与代码冲突。同步契约与 ADR，明确当前内容过滤和历史研究模式，未实现的历史查询不得暗示已验收。

### T04 [P2] 元数据纪元只哈希长度，常见修改不会让游标失效（S08 未闭环）

位置：`app/knowledge/kbapi.py:222-241`。

epoch 输入是文档数和字段长度之和，不是字段值。A/B 文档各两块、symbol 都为 AAA；先返回两条，再把第一页文档 symbol 改为同长度 BBB。epoch **完全相同**，带 AAA 过滤的第二页仍返回 200、0 条、无 next，而另 2 条有效结果被跳过。同长度日期修改、不同文档 available 一增一减也会抵消。

用真实元数据修订号或规范化内容摘要，覆盖过滤依赖的文档/版本/集合字段；查询使用的修订与游标签发须一致。修改后明确 409 或保持合法一致快照，实时撤权仍优先。

### T05 [P1] 漏页仍可 ready，且新质量逻辑未改变处理身份（S05/A03）

位置：`app/knowledge/extract.py:36,711-798`；`app/knowledge/jobs.py:210-221`。

1. 三页 PDF：第 1 页无文字，OCR 返回空、fallback 抛错；其余两页正常。结果仍为 **ready**，unmet_ocr_pages=0，三页状态都显示 text_layer。空结果没有推进失败状态；全空单页测试只是被全文 no_text 兜底拦住，不能证明混合文档的页级完整性。
2. 本轮修改了 PDF 质量行为，却没有更新 EXTRACT_CONFIG/质量版本或解析器身份。基线 `0a473d9` 与当前相同 OCR 配置计算出的 digest **完全相同**（见 JSON）。jobs 在提取前命中旧产物就返回，正常续跑不会应用修复后的质量逻辑。直接宣布“第四轮重提取”不能保证真正处理了旧结果。

空 OCR、未达标且回退失败的页面必须保留明确状态，阻止文档 ready。对影响正文/质量的实现变更维护显式 recipe 版本，旧产物不可原位覆盖；先计划受影响集合与新身份，验证新产物生成及旧引用仍可读，再谈全量。

### T06 [P2] 语义召回仍截断前 200；缓存仍跨 provider 混用（S10 未闭环）

位置：`app/knowledge/analysis.py:85-90,126-134`；`app/knowledge/store.py:849-868`。

两个文档的纯语义召回反例已修复，但 `vector_pool=allowed[:embed_top]` 仍在相似度计算前按数据库枚举顺序截断。205 个允许块中，强语义目标位于第 205 个，查询 **永远无法返回它**。应从整个授权索引做向量召回后取 top-k，或显式声明受限能力，不能称完整语义检索。

缓存仍用 model+block 查询，只增加维度不匹配检查。两个 provider 使用同名 model、相同维度、不同向量空间，第二个 provider **调用 0 次，复用第一个 provider 的向量**。文档说 provider 已隔离，实际只验证不同维度。缓存身份须包含稳定 provider/端点语义身份、model/revision、维度和规范化版本，旧缓存隔离保留。

真实 embedding 继续关闭；这两项已用本地确定性向量复现，无须付费。

### T07 [P2] 追加候选修复后，同一新版本每次导出都会复制（S02/A02）

位置：`app/knowledge/writeback.py:94-104,127-141`。

先生成 v1，再连续三次导出完全相同的 v2，得到 **4 个 Markdown 文件，其中 3 份相同 v2**。manifest 仅跟踪主名，随机候选未按内容/claim revision 去重。长期定时导出会持续污染 Vault。

保持不覆盖人工内容，增加生成对象 ID+revision+模板版本等稳定幂等身份，不能只依赖含运行时间的渲染文本 hash。已发布候选重复投递不得增文件；候选被人工编辑时保留编辑并按明确规则决定是否产生新版本，不得为去重而覆盖或删除。
