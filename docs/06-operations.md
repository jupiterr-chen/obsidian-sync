# 部署、运维与恢复

## 目标拓扑

先部署在原文可达的单台服务器：scheduler、解析 worker、API、单一索引发布者；使用独立 runtime 根目录。Obsidian 客户端继续通过 Syncthing 同步 Markdown。当前没有安装依赖、创建服务器任务或改变生产网络。

运行目录建议：objects/、extractions/、indexes/、state/、logs/、snapshots/。原文写入后不可变；SQLite 活库不放入 Syncthing。备份通过一致性数据库快照和产物清单完成，快照再复制到另一存储。

## 任务状态与恢复

discovered -> queued -> leased -> extracting -> validating -> indexing -> ready -> published。异常进入 retry_wait / quarantined / failed；超时租约可恢复，恢复前检测已有完整产物。失败次数上限初定 3，指数退避和 jitter；永久格式错误不盲目重试。源版本和提取版本唯一约束保证幂等，发布层采用事务性 active 指针。

## 资源和预算

worker 并发由样本 CPU/GPU/RAM 实测决定，初始保守单 worker。每任务设置页数、字节、耗时限制，超大文档分阶段处理。LLM 默认关闭；启用后设置每日预算、单任务输入/输出上限、供应商并发及重试预算。网络重试必须识别已经完成的请求，避免重复计费。

磁盘预算使用原文、页图、OCR 中间件、正文、索引、历史版本、备份分别测量；源文件 1.76 GB 不能代表总空间。页图采用按需生成/可重建策略，具体保留期另定。

## 可观测性

指标：变化发现延迟、队列长度、每格式/页耗时、OCR 页比例、提取失败率、待复核量、active 文档数、索引延迟、检索 P50/P95、引用失效数、模型输入/输出/推理用量及实际成本。

日志默认记录身份和状态，不记录完整正文、客户端 token 或 API key。request_id/job_id/extraction_id 贯穿关联。报警仅用于异常和需人工动作，日常摘要按需查看。

## 恢复与发布

发布前验证 manifest、块数量和引用完整性；旧 generation 保持可回滚。回滚不能覆盖原文或修改人工研究。RPO 目标 24 小时、RTO 目标 4 小时，P6 恢复演练后才可宣称达到。必须在独立测试目录演练，不覆盖实际 Vault。

访问不可达时继续提供现有固定正文和明确源状态；来源临时丢失不当作删除。凭据泄露/撤权时优先阻断查询，不以缓存作为绕过方式。

## 跨设备写入

一个服务写生成区，人工多设备编辑人工区。冲突保留并提示，不自动清理。定时触发采用服务器原生任务调度，保存锁/租约防止上一轮未完成时重复全量扫描。
