# 研报知识库的使用方式与投资研究流程

日期：2026-10-07。状态：下一阶段方案，尚未执行模型试点或新功能部署。

这套知识库的用途，是围绕你关注的公司和问题持续积累证据，帮助你判断新信息改变了什么、原有假设是否仍成立，以及哪些问题还不能下结论。Obsidian 承担阅读与研究笔记；服务器保存资料、版本和研究成果；LLM 按研究任务处理相关证据；投资应用读取可追溯的背景包。

建议先用两家公司、一个研究主题和约十二份质量合格的资料完成试用。先得到一次有价值的研究结果，再扩大自动分析范围。历史正文修复继续独立运行，规划工作不改变它的配置、批次或调度。

## 日常围绕问题使用资料

建议给每家公司建立三到五个长期研究问题。例如“增长来自销量还是价格”“盈利改善能否转化为现金流”“报告的乐观假设最容易在哪个环节失效”。这些是问题模板，不预设任何公司的答案。

收到新资料时，系统按以下顺序处理：

1. 判断关联对象与研究问题，结合关注名单和来源信息排列阅读优先级。不相关或重复资料保留可搜索，不强制做深度分析。
2. 提供一张短阅读卡：资料类型、所属期间、核心新增信息、关联问题、正文质量与原文入口。
3. 对相关资料抽取事实、作者观点、假设、风险和反证。把“作者认为”与“系统推断”分开。
4. 与同公司上一期间、同一指标及不同来源的报告比较，解释哪些差异来自期间、单位、会计口径或预测口径。
5. 生成研究假设的更新候选，列明支持、反对和仍缺失的证据。你确认后形成自己的研究判断。

以一份中期报告为例，使用结果应当包括“相较上一期增加了哪些可核对信息”“哪些研究问题有了答案”“需要追踪什么新问题”。单独把它压缩成一篇摘要，通常不足以支持后续研究。

建议先试行下面的阅读节奏。时间是个人使用建议，不是已创建的自动任务：

| 使用时机 | 先看什么 | 留下什么 |
|---|---|---|
| 每天约十分钟 | 与关注对象有关的新资料、关键变化和待核对事项 | 今天值得深读的一至三条问题 |
| 每周约三十至六十分钟 | 公司判断的变化、相互矛盾的证据、尚未解答的问题 | 更新或保留假设的理由，下一步研究清单 |
| 作出重要决策前 | 当时可用的背景包、反证、资料截止时间和缺口 | 采用的依据版本、自己的判断及复核条件 |
| 后续复盘时 | 当时的冻结记录与之后新出现的证据 | 判断错误、资料遗漏和执行偏差各是什么 |

为帮助真正消化信息，每次深读后用自己的话写三句：我原来怎么想；哪条证据改变或强化了这个想法；什么证据会使我再次改变判断。研究系统保存这三句与引用，后续更新围绕它们进行。

## Obsidian 中的入口

复用现有 Vault 的目录和人工区约定。以下路径结构是拟议布局；本次只在工程 `docs/` 中落地方案，不向生产 Vault 添加页面。

```text
资料目录/                    已有资料卡片与原文入口
解析正文/开始阅读.md          正文入口，继续显示当前可用版本
自动研究候选/                自动生成区，具体子目录需核对写回登记
  研究入口.md                关注对象、重要变化、待确认判断
  单篇分析/                  事实、作者观点、风险、证据
  公司摘要/                  跨期变化、分歧、覆盖范围
  主题摘要/                  跨公司证据及尚不确定的问题
  变化简报/                  只列相较上次新增的有效信息
公司研究/                    现有人工区，保存你认可的判断
主题研究/                    现有人工区，保存你的主题研究
周报与复盘/                  现有人工区，保存研究和决策复盘
分析草稿/                    现有人工区，保留你的草稿
```

“研究入口”优先显示资料名称、公司、报告期间、处理状态和近期变化。哈希、提取版本和候选文件仍作为追溯信息，不要求用户记住文件名。读取顺序是研究入口 → 公司或问题 → 结论和反证 → 原始证据。

旧正文与 `.candidate-*` 副本的治理另行完成：先核对引用和人工修改，再制定保留或归档清单。当前继续保留它们；本方案不授权删除、移动、隐藏整个正文目录或修改同步规则。阅读入口改善可独立实施，不必等待历史文件治理完成。

公司研究、主题研究、周报与复盘、分析草稿的 README 明确它们属于人工区。后续自动页面不得因为目录名字合适就写入这些区域。自动稿与人工稿分别保存，用链接关联；确认一项候选不等于允许覆盖整篇人工笔记。

## 三个使用界面共享同一套证据

| 界面 | 最适合的工作 | 数据取得方式 |
|---|---|---|
| Obsidian | 阅读、长期公司研究、个人判断与复盘 | 服务器发布的 Markdown 加人工笔记 |
| 研究问答入口 | 临时追问、跨文档比较、寻找反证 | 调用检索接口取得允许范围内的原文块，再交给 LLM |
| 投资或研发应用 | 读取研究背景、保存本次决策依据 | 认证 API 与版本固定的背景包 |

研究问答入口先复用你已有应用或 agent 的调用能力，必要时增加一个薄客户端。Obsidian 聊天插件、独立网页或 MCP 适配均是可选接入方式，当前不假定已经连通。一个聊天窗口也不会天然拥有本地 Vault 或服务器的访问能力。

问答应支持这样的任务：“只用指定两家公司在某截止时间前的资料，比较现金流质量；逐条给出处，指出口径不能比较的项目，并列出缺失数据。”检索要兼顾支持证据和反证，覆盖不同期间与独立来源，不能只抓相似度最高的几个段落。

暂时用现有关键词检索和公司、主题、期间筛选。先记录哪些真实问题找不到答案，再判断是否需要 embedding 或重排。相同公告被不同渠道转载，应识别为同一证据来源，避免把重复转载当作多个独立支持。

## 把信息保存为可复用的研究记忆

| 记忆 | 保存内容 | 更新方式 |
|---|---|---|
| 证据 | 原文快照、正文块、页码、表格位置与来源版本 | 新版本追加，旧引用仍可追溯 |
| 研究 | 事实、作者观点、假设、反证、适用期间与确认状态 | 新证据形成更新候选，保存变化理由 |
| 决策 | 当时研究背景、个人判断、约束、行动理由与后续复盘 | 冻结当时依据，追加复盘 |

LLM 的会话上下文承担本次处理，文件与数据库承担长期记忆。每次只调取与问题有关的内容；重要结论回到原始证据复核，避免反复总结旧摘要导致遗漏和失真。

每条可用于比较的事实至少包含：实体、指标、数值、单位及币种、所属期间、会计或统计口径、实际值或预测值、来源作者、源版本与提取版本、页码或块位置、核对状态。缺失字段明确为空，不能由模型补猜。

资料披露时间、系统首次接入时间、指标所属期间、模型分析时间分别保留。一份新接入的旧财报仍是历史资料。不同期间不能直接比较，币种换算、百分比与百分点、GAAP 与调整后口径应先由规则核对。

对关键数字采用程序计算并记录输入和公式；重要原始数字对照 PDF 表格。LLM 解释数字与假设的关系，不承担唯一的算术或准确性验证。模型自报置信度不作为事实已核实的依据。

## LLM 在哪里发挥作用

| 工作 | 建议方法 | 输出 |
|---|---|---|
| 去重、版本、解析、常规 OCR、索引、用量统计 | 现有确定性流程及本地 OCR | 可定位的正文与处理状态 |
| 资料相关性与粗分类 | 元数据、关注规则优先，含混时再用 LLM | 关联公司、主题和问题 |
| 单篇分析 | 成本受控的文本模型，长文按章节分析并标明覆盖 | 带证据的短结论、事实与风险 |
| 公司或主题比较 | 结合新原文、既有分析、已确认假设的 LLM | 变化、分歧、反证与更新候选 |
| 疑难页核对 | 原生解析或本地 OCR 优先；视觉模型单列可选范围 | 需要复核的页与识别证据 |
| 资金约束、指标计算、交易执行 | 投资应用的确定性规则与人的决定 | 可审计的检查与决策记录 |

成本按三档控制：所有资料可索引；关注对象做单篇分析；只有重要问题或明显冲突进入深度综合。对已有结果按源版本、提取版本和分析配方复用，变化时只更新受影响对象。历史资料先按需求补齐，不默认对整个知识库进行多轮总结。

先用同一组真实资料比较一至两个候选模型的事实准确性、引用支持度、长文遗漏、失败重试与实际账单，再选 provider。选定前不填模型排名或现行价格。启用时确定资料允许清单、模型、是否允许外发、请求上限、输入输出 token 上限和金额上限。

用量预算应包含章节输入、提示词、重叠段落、最终合并、公司总结、输出和重试。全库文本 token 与一次完整研究工作流的 token 不相等。[早期预算文档](09-llm-and-token-budget.md)是情景估计，不能沿用为本次实际报价。

本轮方案编写没有触发后台 provider 调用、付费 API 或新增资料外发。后续 B4 需要明确上述提供者和范围；用户已经授权的服务器正文修复照常执行，无需再次批准。

## 如何接入投资框架

知识库负责回答“证据是什么、判断依据是什么、有哪些反证、何时有效”。投资应用再结合自己的行情、估值、持仓、现金、风险约束和执行规则处理。研报库没有自动覆盖这些实时输入；数据缺失或过期时应明确显示。

现有接口 `POST /api/kb/v1/background-package` 接收 `entity_type`、`entity_id`、`filters.as_of`、`filters.as_of_mode` 和 `limit`，返回来源、claim、风险反证、时间说明与结果摘要哈希。它是接入基础；研究问题专用字段、完整风险结构和目标应用 UI 仍需按场景对接，不能把所有下列目标字段当作现成响应。

拟在目标应用中保存的决策背景记录至少包括：公司或主题、研究问题、信息截止时间、来源覆盖和缺口、关键事实、已确认与待确认观点、反证、证据版本、背景包哈希、个人决策理由以及下次复核条件。应用保存实际使用的包，不能日后用“当前最新包”冒充历史依据。

历史查询需说明是在问“当时本系统已经掌握什么”（system），还是“当时已公开什么”（public）。公开时间未知时明确缺失；晚到或后来修订的资料不得悄悄进入历史判断。历史重放还需要足够的原始来源覆盖，不把本库结果当成完整市场信息。

先完成一次只读集成：选一家公司 → 查询背景 → 打开证据 → 记录判断 → 新资料到来 → 重放旧判断。账户连接、自动下单与新风控规则不属于本轮研究接入。研发应用可复用同一过程，把公司与投资判断替换为技术方案、试验依据和工程决策。

## 下一步交付安排

沿用既有 A 至 E 交付链和 B4 验收，不另起一轮基础架构建设。本表是待执行方案，不是开发派单或生产发布授权。

| 阶段 | 范围与交付 | 可观察的通过条件 |
|---|---|---|
| 准备研究试点 | 定两家公司、一个主题、三至五个研究问题；选约十二份真实资料并核对关键页；形成研究模板与小批预算 | 有固定资料清单、问题清单及人工核对的事实；旧乱码稿不混入，未选资料不处理 |
| B4 真实模型小批 | 复用 B/C，生成单篇分析及两家公司、一主题的自动候选页面 | 重要结论有有效且实际支持它的来源；数字、期间和口径正确；有冲突和缺口说明；同版重试不重复付费 |
| 连续新增资料试用 | 在已批准范围加入后续资料，跑通发现、解析、分析、公司更新、Windows 同步 | 用户无需导出命令即可看到“本次改变了什么”；无关对象不更新；人工稿保持；失败和预算等待可见 |
| 投资应用只读接入 | 使用现有背景包接口对接一个实际页面或调用点，保存采用版本 | 真实应用能查看证据并重放旧判断，知识更新不改写旧记录 |
| 扩大覆盖 | 根据使用价值扩充关注对象、历史资料和研究问题；按实测决定更强模型或检索增强 | 单次新增的成本、延迟与质量可查；没有新增材料时不重复分析 |

十二份样本是建议规模，可按可用资料调整。建议覆盖财报、研报、扫描 PDF 和 HTML，包含长文、同公司跨期资料，以及观点冲突的不同来源。资料合格但不在模型允许清单内，也不能发送。未修复文档只记录缺口，不拖延合格子集试用。

小批先准备约二十条人工核对事实及十个问题，其中包含资料不足、不能回答的问题。记录分母与错误样例：结论支持度、关键数值正确性、范围覆盖、拒答表现、实际成本和从新增到可读结果的时间。验收的中心是一份有用的公司研究结果与一次变化更新，而不是新增多少测试或输出多少摘要。

误述关键数值或期间、引用不能支持核心判断、越界外发、预算失控、覆盖人工内容会阻断受影响能力；限制在实际受影响的范围内修复。页面布局、名称美化、非关键历史副本展示等进入 fix 清单，不把它们变成全项目返工理由。新增建议单列，不回溯扩充已经通过阶段的交付范围。

后续新增代码先完成独立验收，再取得用户对固定 commit 和范围的生产发布授权；开发、自测、提交推送不授权部署。模型费用和资料外发另明确范围。当前 `9d1b04f` 的历史正文修复授权继续有效，不被本方案重新设门槛。
