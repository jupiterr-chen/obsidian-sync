# LLM 使用边界与全量 Token 预算

日期：2026-10-01。当前523份（476 PDF / 31 HTML / 15图片 / 1文本），文件字节合计约1.756GB。原文服务读取超时，本地仅有卡片及清单，**尚未实测正文长度、页数、语言比例和token**。以下区间用于预算情景，不是统计置信区间。

## 哪些地方需要模型

|工作|生成式LLM必要性|费用计量|
|---|---|---|
|清单发现、去重、哈希、版本|不需要|CPU/存储|
|文字PDF、HTML、纯文本提取|不需要|CPU/存储|
|本地OCR与布局|通常不需要生成式LLM|CPU/GPU/页；内部OCR模型不是聊天LLM|
|关键词索引与检索|不需要|CPU/存储|
|语义检索embedding|需要embedding模型，可本地运行|API按其tokenizer，或本地算力；不是生成式分析|
|rerank|可用本地专用模型，LLM可选|查询×候选/模型定价|
|复杂图表、疑难OCR复核|多模态LLM可选|图像/视觉token，不能按正文token直接估算|
|摘要、风险/反证提取、跨期对比|建议使用生成式LLM|输入、输出、推理、重复上下文|
|研究记忆更新建议、综合研究|建议使用生成式LLM|按任务召回证据，非全库每次重读|
|精确财务计算、版本保存、确认流程|不需要|确定性计算与人工确认|

P1-P3 可以做到生成式LLM调用为0。选择模型前先完成正文质量基线。工程开发模型的用量与523份资料分析用量属于不同预算，不能用语料token估计工程实现需要多少模型配额。

## 全量正文的情景假设

假设“每份已经提取、去除重复页眉导航后的平均token”为下表；中英文真实tokenizer差异已经包含在未知平均值中，不能再把它解释为实测转换率。

|格式|数量|低情景平均token|中情景平均token|高情景平均token|
|---|---:|---:|---:|---:|
|PDF|476|8,000|25,000|60,000|
|HTML|31|20,000|50,000|120,000|
|图片|15|500|1,500|4,000|
|文本|1|2,000|5,000|20,000|
|全库合计||4,437,500|13,477,500|32,360,000|

因此可以先按**约440万—3240万正文token，中情景约1350万**比较供应商，范围很宽且不构成上限。年度财报、OCR乱码、巨型HTML、表格投影会显著改变结果。中文不能统一套用英文“4字符/token”。不同tokenizer也会产生不同计数。

## 不同工作流预算

1. 全量抽取+OCR+关键词：0生成式LLM token；不是0计算成本。
2. 全量embedding：假设重叠/标题/表头额外20%，低/中/高为5.33M / 16.17M / 38.83M embedding输入token。20%是情景参数，实测后替换。
3. 每份一次摘要：输入正文+每份1000提示token，约4.96M / 14.00M / 32.88M；若每份输出1000-2000token，则输出0.523M-1.046M。超长文档分块汇总另增加调用及上下文。
4. 逐块事实提取再文档汇总：假设正文重复1.3-2倍，输入约5.77M-64.72M，再加逐调用提示词；输出取决于schema和事实密度，必须先跑样本。不能将正文一遍成本当多轮成本。
5. 日常研究：只检索相关证据；若每问上下文20k-80k并输出2k-6k，则100问约2M-8M输入、0.2M-0.6M输出，另有提示词、重排、推理与重试成本。此参数也是示例预算。
6. 多模态补救：单独按页图分辨率、模型视觉计费和页数测量，不加入上表作为已知token。

以上 input 不含额外 reasoning；供应商若将推理计入output，必须按其账单类别避免二次计费。embedding与聊天tokenizer不同，不能直接复用对方精确计数。

## 价格比较公式

`成本 = 输入M × 输入单价 + 缓存输入M × 缓存单价 + 输出M × 输出单价 + 独立推理费用 + 图像/工具费用`

输入与缓存输入分开，不能将同一token计入两项。推理如果已经计入output不再另加。仅用示例价格演示：中情景一次摘要输入14.00M、输出0.785M（每份1500）；若供应商报价输入1美元/M、输出5美元/M，则约17.93美元；报价输入5、输出25，则约89.63美元。这些不是任何模型的当前报价，不包含重试、图像或分块二次汇总。

预留10%-20%失败重试预算属于可调整预算参数。Batch/cache优惠不能预设，按供应商实际支持和工作流命中率核对。

## 实测方法（P1-04）

- 取得源原文，按格式与语言分层选30份；提取正文并记录真实页数、扫描页数、表格投影、提取质量。
- 使用候选模型对应tokenizer精确计数；不支持本地tokenizer时用供应商计数接口，说明是否外发及费用。
- 每份记录document key/source hash/extraction配置/text hash/tokenizer版本/token数；保存未提取名单和coverage。
- 分层均值×该层份数，报告中位数/P90、极端值及bootstrap区间；30份的统计区间不保证覆盖未观察到的巨型文档。
- 全量完成提取后，对正文全量计数，不调用生成模型，也不产生聊天输出费用。
- 对20份样本执行固定分析任务，测量输入/输出/推理/延迟、引用准确率及重试率，再决定模型和全量预算。

## 模型选择策略

批量摘要与结构化提取先比较低成本模型；复杂表格或失败案例升级较强模型；跨文档研究及反证综合按需使用强推理模型。embedding单独选型。保持provider适配层、model与prompt版本及评测集，避免以“参数量大”代替实际质量。

在候选模型尚未指定时，不填虚构价格或宣称某模型最优。用户给出候选名称、供应商和账户价格后，使用本预算及样本真实计数做同任务成本/准确率表。

## 官方参考

OpenAI官方说明可对完整请求计数，文本之外的工具和图像也影响输入；输出与推理账单要按实际usage解读：[Counting tokens](https://developers.openai.com/api/docs/guides/token-counting)。不同供应商须使用各自对应规则；本设计不绑定OpenAI。
